# 拼多多搬家助手（Chrome 扩展）

在拼多多商品页一键把商品推送到本地「煤炉多账号管理台」，由管理台自动翻译成日语、
按公式换算日元价格，再发布到 メルカリ / Yahoo!フリマ。

拼多多的风控不允许在指纹浏览器里访问，所以采集这一步放在日常使用的 Chrome 里，
通过本扩展把商品数据中转给本地管理台。

## 安装

1. Chrome 打开 `chrome://extensions`
2. 右上角开启「开发者模式」
3. 点「加载已解压的扩展程序」，选择本仓库目录

## 使用

1. 确认本地管理台服务已启动（默认端口 8791）
2. 打开任意拼多多商品页（`mobile.yangkeduo.com` / `mobile.pinduoduo.com`）
3. 点击页面右下角红色的「搬到管理台」按钮

   多规格商品会**按款式/颜色自动拆成多件独立商品**，各带自己的价格和主图——
   因为煤炉一个链接只能卖一件。一次最多拆 20 件，不要的在采集箱里删掉即可。

   服装类常见「颜色 × 尺码」两个维度（8色×6码=48个组合），**不会**拆成 48 件：
   按颜色拆成 8 件，可选尺码写进商品说明，定价取该颜色下最贵的尺码（避免大码亏本）。
4. 到管理台的「搬家上架」页确认标题/价格/分类，选择发布目标后上架

## 配置

点击浏览器工具栏上的扩展图标可设置管理台服务器地址，并用「测试连接」验证是否连通。
留空时自动依次尝试：本机 → Tailscale → 局域网。

### 异地使用（浏览器和管理台不在同一个局域网）

两台设备装 [Tailscale](https://tailscale.com/) 登录同一账号，在跑管理台的机器上执行一次：

```
tailscale serve --bg --tcp 8791 tcp://127.0.0.1:8791
```

之后在任何一台 tailnet 内的设备上都能用 `http://<设备名>.<tailnet>.ts.net:8791` 访问，
把这个地址填进扩展弹窗保存即可（保存时 Chrome 会弹窗请求该地址的访问权限，必须允许）。

> 扩展只能请求 `host_permissions` / 已授权的地址。换了新的服务器地址一定要点「保存」走一次授权，
> 否则请求会被 Chrome 直接拦掉。

## 工作原理

| 文件 | 作用 |
|---|---|
| `content.js` | 在商品页注入悬浮按钮，监听 SPA 路由变化重新挂载 |
| `background.js` | 把 `extract.js` 注入商品页取数据，POST 给管理台；定时核查原链接是否下架 |
| `extract.js` | 取数核心，注入页面主世界运行，采集和下架核查共用。只读页面，不改任何东西 |
| `popup.html` / `popup.js` | 设置管理台服务器地址 |

### 商品数据从哪来

拼多多的商品页有两种版本，扩展两种都要对付：

1. **服务端渲染**：HTML 里带一段 `window.rawData = {...}`，商品数据直接读全局变量。
2. **客户端渲染**（HTML 约 47KB，里面写死 `window.rawData=null`）：页面加载后自己 POST
   `/proxy/api/api/oak/integration/render` 拿数据，存进 MobX store，**全局变量和 HTML 里都没有**。
   这种页面只能顺着 DOM 节点上的 `__reactFiber$…` 爬到 React 根，扫组件的 props / state，
   找到 store 后调它的 `toJSON()`——吐出来的形状和 `rawData.store` 一样。

几条硬规矩（都是踩过的坑）：

- **商品号必须和地址栏对上**。从搜索页点进来时，内存里同时躺着几十个搜索结果、推荐位的商品，
  认「第一个像商品的对象」会把别人的商品推上去。对不上宁可报错。
- **只有摘要不算数**。列表卡片也带商品号和名字，但没有规格和相册，拿它推上去是残缺数据。
- **价格单位在扩展里定死**，统一发整数「分」。接口给整数分，老页面给小数元（`"19.3"`），
  整元（`"46"`）如果交给服务端按「整数=分」去猜，就成了 0.46 元。
- **不包 fetch / XHR，不自己调接口**。拼多多的反爬脚本会检测原生函数有没有被改；
  自己调接口要 `anti_content` 签名，被风控标记的账号连在售商品都会显示「已售罄」。

未登录拼多多时页面只有壳数据，扩展会提示「拼多多没登录」。

### 下架核查

后台每 3 小时开一个不激活的标签页逐个查。**一次核查里连续两次读到下架迹象才回报下架，
管理台那边还要连续两轮（隔几小时）都这么说才发邮件**——早期版本读不到商品名就判下架，
把在售商品冤枉过，宁可漏报也不误报。

## 依赖

需要配套的本地管理台服务提供 `POST /api`（`action: "pdd_push"`）接口接收数据。
